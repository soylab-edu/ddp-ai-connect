| 미디어 클릭 | 고정 라이트박스 열림, 배경 스크롤 잠금 | 849–870줄 |
| 라이트박스 닫기 | 닫기 버튼·배경 클릭·Esc로 닫기 | 853–855줄. stage를 비워 재생 요소 제거 |
| 원문 열기 | 새 탭의 원문 주소 제공 | 영상용 fallback 링크. 오류 시 자동 전환은 없음 |

라이트박스 트리거는 YouTube 39개, Drive 10개, MP4 27개, 이미지 41개다. 이는 고유 미디어 파일 수가 아니라 클릭 가능한 트리거 수다. YouTube는 nocookie iframe, Drive는 preview iframe, MP4는 video 요소, 이미지는 img 요소를 만들어 표시한다. 실제 재생 가능 여부는 외부 제공자·로그인·권한에 따라 달라지며 이번에 재생 시험을 하지 않았다.

**인터랙션의 주요 문제**

1. **A등급 필터의 숨김 방식이 CSS와 충돌한다.** JavaScript는 `it.hidden = true`를 사용하지만 모든 대상은 `.ar { display:grid }`를 가진다. 일반적인 CSS 캐스케이드에서 작성자 display 규칙은 hidden의 기본 숨김 스타일을 덮을 수 있다. 원본에는 `.lb[hidden]`만 있고 `.ar[hidden]` 처리는 없다. 선택 버튼만 바뀌고 목록이 남는 문제가 예상된다. 코드 결함으로 식별했으며 실행 재현은 아직 하지 않았다. 수정 시 `.ar[hidden] { display:none!important }`처럼 대상을 명확하게 처리해야 한다.

2. **이미지 확대 41개가 키보드로 활성화되지 않는다.** 전부 `span role="button" tabindex="0"`이지만 Enter·Space 처리 없이 click만 듣는다. Tab으로 도달 가능한 것과 키보드로 실행 가능한 것은 다르다. 실제 button 요소로 바꾸는 것이 우선이다.

3. **라이트박스 포커스 관리가 없다.** dialog/aria-modal 표시는 있으나 열릴 때 포커스 이동, 내부 포커스 유지, 닫힐 때 원위치 복귀가 구현되어 있지 않다. 배경에 inert 처리도 없다. 동적으로 삽입하는 iframe에는 title이 없고 확대 이미지에는 빈 alt가 들어간다.

4. **재생 실패 안내와 실제 동작이 다르다.** 목차에는 ‘재생이 막히면 원문이 열립니다’라고 적혀 있지만 오류 감지·자동 이동 코드는 없다. 실제 기능은 사용자가 ‘원문 열기’를 누르는 방식이다. 안내 문구를 이 동작에 맞추면 된다.

5. **검색·정렬·필터 상태 복원은 없다.** 333건 규모로 소개하는 긴 자료집이지만 A 목록에만 분류 필터가 있다. 검색, 정렬, URL 필터 반영, 결과 건수 알림은 구현되어 있지 않다. 읽기 경험을 개선한다면 새로운 장식보다 탐색 기능의 효과가 클 수 있다.

**6. 모션그래픽의 구성과 시간표**

표지는 렌더링된 동영상이 아니라 **HTML 요소·SVG·CSS 3D 변환과 81개의 CSS keyframes**로 구성된다. 본문에 있는 Canvas·Three.js라는 단어는 소개 대상의 설명이며, 이 문서의 표지 엔진을 뜻하지 않는다. 표지에 영상·오디오 재생 요소나 Canvas/WebGL 렌더러는 없다.

메인 사이클은 16초다. 모든 장면이 같은 주기를 공유하며 `visibility`를 `steps(1,end)`로 바꿔 컷을 전환한다. HUD는 8개 장면으로 표시한다. 코드의 실제 쇼릴 패널은 10개이고, 네 개의 짧은 텍스트 컷을 한 장면처럼 묶으며 마지막 정보 표지는 쇼릴 밖에 배치되어 있다.

S3의 이동 곡선은 linear, ease-in-out, ease-out, ease-in, back-out, elastic으로 다르다. 모델별 실제 성능이나 날짜의 연속 시계열을 계산한 차트가 아니다. ‘출시 곡선’이라는 레이블과 모델 이름을 사용한 연출이다. 분석 차트와 같은 의미로 재사용하면 오해를 만들 수 있다.

S4는 `clip-path:polygon(...)`의 모든 상태를 40개 좌표로 맞춰 형태를 보간한다. 스마일은 polygon이 그대로 변하는 것이 아니라 별도 SVG가 나타나는 방식이다. S5는 데스크톱 16열, 모바일 8열이며 HTML 타일 수는 동일하다. S6 역시 JavaScript 입자 시뮬레이션이 아니라 미리 기록된 점의 `rotateY / rotateX / translateZ` 좌표와 부모 회전이다.

보조 모션은 배경 심벌의 40초 회전, 눈의 4초 깜빡임, 48초 티커, 16초 HUD 진행 막대·장면 번호·타임코드다. 이 주기들이 모두 16초에 맞춰 초기화되는 것은 아니므로 매 루프의 보조 요소 위치가 완전히 동일한 영상처럼 반복되지는 않는다.

**모션의 강점과 한계**

강점은 확대·회전·시차·형태 변화·빠른 컷·타이포를 서로 다른 장면에 배분했다는 점이다. 한 가지 효과를 계속 반복하지 않고, 심벌에서 월 표기와 기술 키워드를 거쳐 정보 표지로 수렴한다. 영상 자산 없이 해상도에 반응하고, 문구를 HTML에서 교체할 수 있다.

가장 큰 사용성 문제는 **11초까지 실제 정보 표지가 쇼릴에 가려지고, 하단 CTA까지 완성되는 시점은 약 12.4초**라는 점이다. 그 뒤 와이프 시작까지 안정적으로 읽을 시간은 약 3.2초뿐이다. 스크롤 자체를 막는 코드는 없지만, 표지를 보고 기다리는 독자의 탐색 시작은 늦어진다. 문서형 서비스라면 첫 재생 뒤 정지, 재생·일시정지, 항상 보이는 ‘본문 바로 보기’를 우선 검토할 만하다.

`prefers-reduced-motion:reduce` 대응은 명시되어 있다. 쇼릴과 와이프를 제거하고 애니메이션·전환·부드러운 스크롤을 끈다. 하지만 수동 모션 제어는 없고, 화면 밖으로 나간 표지의 애니메이션을 정지시키는 코드도 없다. 미디어쿼리와 브라우저의 자체 최적화 효과는 실제로 시험해야 한다.

성능은 transform·opacity 중심이라는 장점이 있지만, `left` 이동, 40점 clip-path, blur/drop-shadow, 색상 변화도 포함한다. 따라서 모든 효과가 저비용 GPU 합성만으로 처리된다고 단정할 수 없다. 특히 모바일에서 144개 패턴·150개 점·본문 DOM의 조합은 프레임률 측정이 필요하다. 이번에는 성능 저하를 실측하지 않았다.

JavaScript에 있는 ‘표지 숫자 카운트업’ 코드는 `[data-count]`를 찾지만, 해당 속성을 가진 요소가 0개다. 현재의 8·26·333·51은 **카운트업 없이 표시되는 숫자**다. 남아 있는 코드만 보고 기능이 작동한다고 판단하면 안 된다.

유지보수 측면에서는 디자인 토큰과 공통 클래스가 잘 정리되어 있지만, 콘텐츠·배치·이미지 데이터·모션 타이밍이 한 파일에 결합되어 있다. 여러 곳에 반복한 건수·등급·링크를 손으로 갱신하면 어긋나기 쉽다. 편집용 데이터·CSS·동작 코드는 분리하고, 배포 때 하나의 HTML로 묶는 구조가 현재의 전달 편의성을 유지하기 좋다.

**8. 후속 디자인에 가져갈 원칙**

가져갈 요소는 넓은 모션 표지와 제한된 폭의 본문 대비, 숫자 중심의 챕터 헤더, 일정한 카드 구조, ‘요약 표 → 상세 사례 → 원문’의 읽기 순서, 미디어의 cover/contain 구분, 낮은 우선순위 자료의 접기다. 빨강과 검정을 복사하는 것보다 이 정보 위계를 보존하는 편이 원본의 성격을 잘 이어간다.

변경할 우선순위는 첫 화면의 즉시 탐색, 필터의 실제 숨김, 키보드·모달 포커스, 숫자·링크 집계의 일관성이다. 본문 스크롤 애니메이션을 추가하기 전에 이 부분을 정리하면 연출과 문서 사용성이 함께 좋아진다.

실제 화면 검증은 아직 남아 있다. 데스크톱·모바일의 대표 폭에서 표지 1루프, 각 챕터 배치, 분야 필터, 키보드 확대·닫기, 외부 미디어, 다크 모드, 모션 감소 설정을 확인해야 이 분석의 시각적·실행상 결론을 확정할 수 있다.
